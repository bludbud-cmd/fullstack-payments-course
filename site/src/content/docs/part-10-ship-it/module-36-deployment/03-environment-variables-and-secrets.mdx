**Goal:** By the end of this lesson you can say where each of PayDeck's settings belongs, fill in a server's `.env` safely, and make the API name every missing setting before it touches the database.

## Why it matters

The same image runs on your Mac, on a test server and on the real one. What differs is the **settings**: which database, which signing key, which address. Get one wrong on a server and the API either fails with a confusing message, or, worse, starts with a development value: a signing key printed in a public repository, or pretend top-ups switched on for real customers. Lesson 30.7 started a check for this. Deployment is where it earns its keep.

## The idea

### Three places for a setting

| Where | What goes there | PayDeck example |
|---|---|---|
| `application.yml` (in Git) | Defaults that work on your Mac, and the **names** of the environment variables that override them | `${DATABASE_URL:jdbc:postgresql://localhost:5432/paydeck}` |
| `application-production.yml` (in Git) | Settings every server shares, and that are not secret | graceful shutdown, `simulated-top-ups` off |
| `.env` on the server (never in Git) | Secrets, and what is different for each server | `JWT_SECRET`, `DATABASE_PASSWORD`, the public address |

The rule from lesson 30.7 still holds: code holds **names**, never secret **values**.

### Fail loudly, and first

A missing setting should stop the API at start-up with a sentence that says what to set. And it should stop it **before** anything else can fail because of the same missing setting, or the first error you see will be about something else.

## Worked example

### The settings file

`.env.example`, committed, lists every setting a server needs, with no real values:

```sh
# Settings for compose.production.yaml. Copy to .env (which git ignores) and fill in.
# Never commit the real file: these values let anyone run your API as you.

# openssl rand -base64 48
JWT_SECRET=
# openssl rand -base64 24
DATABASE_PASSWORD=
# The API's own address, as the internet sees it.
PAYDECK_PUBLIC_BASE_URL=https://api.example.com
# Stripe test mode (Module 31). Empty switches card top-ups off.
STRIPE_SECRET_KEY=
STRIPE_WEBHOOK_SECRET=
# true lets people add pretend money, for a demo server.
PAYDECK_SIMULATED_TOP_UPS=false

# Google sign-in (Module 29). Remove the # from both lines to switch it on;
# an empty client ID stops the API from starting.
# SPRING_SECURITY_OAUTH2_CLIENT_REGISTRATION_GOOGLE_CLIENT_ID=
# SPRING_SECURITY_OAUTH2_CLIENT_REGISTRATION_GOOGLE_CLIENT_SECRET=

# Push notifications (Module 34): path to the Firebase key inside the container.
# Empty: notifications are only written to the log.
FIREBASE_SERVICE_ACCOUNT_FILE=
```

- `JWT_SECRET` signs every access token (lesson 27.5). Make a new one for each server, on that server.
- `DATABASE_PASSWORD` is read twice by Compose: by the `postgres` service to create the database user, and by the API (through `env_file`) to log in. One value, both sides agree.
- `PAYDECK_PUBLIC_BASE_URL` is where Stripe sends a browser back after a card top-up (lesson 31.3). On a server it must be the `https://` address Caddy serves.
- `PAYDECK_SIMULATED_TOP_UPS=false`: on a server, money comes in only through Stripe, unless you deliberately run a demo.
- Google sign-in is commented out: Spring reads an empty client ID as "configured, but broken" and refuses to start, so "off" means the line is not there at all.
- `FIREBASE_SERVICE_ACCOUNT_FILE` is a **path**. The key file itself goes on the server next to `.env`, and Compose can mount it into the container (the project shows how).

On the server, after filling it in:

```sh
chmod 600 .env
```

`600` means only the file's owner can read or write it. Other accounts on the server cannot read your secrets.

`.gitignore` already ignores `.env` (lesson 30.7), and lesson 36.1's `.dockerignore` keeps it out of the image. Check before every first commit of a new project:

```sh
git check-ignore -v .env
```

```
.gitignore:5:.env	.env
```

### The production profile

`application-production.yml` gets the settings every server shares:

```yaml
# Extra settings for the deployed API, on top of application.yml.
# Turn them on with the environment variable SPRING_PROFILES_ACTIVE=production.
# ProductionSettingsCheck refuses to start if a required setting is missing.
spring:
  main:
    banner-mode: off

management:
  endpoint:
    health:
      show-details: never

paydeck:
  environment: production
  # Real money only: top-ups come through Stripe. Set to true for a demo server.
  simulated-top-ups: ${PAYDECK_SIMULATED_TOP_UPS:false}

server:
  # The host's proxy handles HTTPS and passes on the original address in
  # X-Forwarded-* headers, so links the API makes (Google, Stripe) use https:// too.
  forward-headers-strategy: framework
  # Finish requests already in progress before stopping for a new release.
  shutdown: graceful
```

- `simulated-top-ups` defaults to `true` in `application.yml` (handy on your Mac), and to `false` here.
- `forward-headers-strategy: framework`: the API sees requests from Caddy, over plain HTTP. Caddy adds headers saying "the original request was `https://api.yourdomain.com`", and this setting makes Spring believe them. Without it, the address the API builds for Google's sign-in callback starts with `http://`, and Google refuses it.
- `shutdown: graceful`: when Compose replaces the API with a new version, requests already in progress (a payment, say) finish first.

### A check that came too late

Lesson 30.7's `ProductionSettingsCheck` only checked `JWT_SECRET`. The course added the two other server settings to its list, built the image, and ran it with no settings at all (lesson 36.1's `docker run --rm paydeck-api`). It expected three friendly sentences. It got this instead:

```
WARN 16778 --- [paydeck-api] [           main] org.hibernate.orm.jdbc.error             : Connection to localhost:5432 refused. Check that the hostname and port are correct and that the postmaster is accepting TCP/IP connections.
org.hibernate.exception.JDBCConnectionException: Unable to obtain isolated JDBC connection [Connection to localhost:5432 refused ...
```

The check never ran. It was a `@Component`, so Spring created it along with all the other beans, and Spring happened to create Flyway's first: Flyway connected to the default database address, failed, and stopped the start-up. The friendly message was waiting in a bean that was never reached. Someone deploying for the first time would spend an hour on database networking, when the real problem was three missing lines in `.env`.

The fix is to run the check at the very start, before Spring creates any bean. Spring Boot announces each stage of starting with an **event**, and the earliest useful one is `ApplicationEnvironmentPreparedEvent`: "all settings have been read, nothing has been created yet". A listener for it:

`src/main/java/dev/paydeck/api/common/ProductionSettingsCheck.java`:

```java
package dev.paydeck.api.common;

import java.util.ArrayList;
import java.util.List;
import java.util.function.Function;

import org.springframework.boot.context.event.ApplicationEnvironmentPreparedEvent;
import org.springframework.context.ApplicationListener;
import org.springframework.core.env.ConfigurableEnvironment;

/**
 * Refuses to start a deployed API that still has the settings meant for your
 * own Mac. Runs only with {@code SPRING_PROFILES_ACTIVE=production}: a clear
 * message at start-up beats a guessable signing key later.
 *
 * <p>It listens for the moment the settings are read, before anything else
 * starts (even the database connection), so a missing setting is reported
 * first. {@link dev.paydeck.api.PayDeckApplication#main} registers it.
 */
public class ProductionSettingsCheck implements ApplicationListener<ApplicationEnvironmentPreparedEvent> {

    @Override
    public void onApplicationEvent(ApplicationEnvironmentPreparedEvent event) {
        ConfigurableEnvironment environment = event.getEnvironment();
        if (!environment.matchesProfiles("production")) {
            return;
        }
        List<String> problems = problems(environment::getProperty);
        if (!problems.isEmpty()) {
            throw new IllegalStateException("PayDeck is not ready for production:\n  - "
                    + String.join("\n  - ", problems));
        }
    }

    /** Each problem as a sentence. {@code settings} reads an environment variable. */
    public static List<String> problems(Function<String, String> settings) {
        List<String> problems = new ArrayList<>();
        String secret = settings.apply("JWT_SECRET");
        if (secret == null || secret.length() < 32) {
            problems.add("Set JWT_SECRET to a long random value, for example from: openssl rand -base64 48");
        }
        String database = settings.apply("DATABASE_URL");
        if (database == null || !database.startsWith("jdbc:postgresql://")) {
            problems.add("Set DATABASE_URL to jdbc:postgresql://HOST:5432/DATABASE (and DATABASE_USERNAME, DATABASE_PASSWORD)");
        }
        String publicUrl = settings.apply("PAYDECK_PUBLIC_BASE_URL");
        if (publicUrl == null || !publicUrl.startsWith("https://")) {
            problems.add("Set PAYDECK_PUBLIC_BASE_URL to the API's own https:// address");
        }
        return problems;
    }
}
```

What changed from lesson 30.7:

- No `@Component` and no `@Profile`: it is not a bean any more. It `implements ApplicationListener<ApplicationEnvironmentPreparedEvent>`, an interface with one method, `onApplicationEvent`, which Spring calls when that event happens.
- Because `@Profile` only works on beans, the listener checks the profile itself: `environment.matchesProfiles("production")`.
- The rule, `problems`, is still a `static` method, now with three checks.

A listener that must run before any bean exists cannot be found by Spring's scan (which creates beans), so `main` registers it by hand. `PayDeckApplication.java`:

```java
    public static void main(String[] args) {
        SpringApplication app = new SpringApplication(PayDeckApplication.class);
        // Checked before anything else starts, even the database connection.
        app.addListeners(new ProductionSettingsCheck());
        app.run(args);
    }
```

Rebuild the image and run it with no settings again:

```sh
docker build -t paydeck-api .
docker run --rm paydeck-api
```

```
ERROR 1 --- [paydeck-api] [           main] o.s.boot.SpringApplication               : Application run failed

java.lang.IllegalStateException: PayDeck is not ready for production:
  - Set JWT_SECRET to a long random value, for example from: openssl rand -base64 48
  - Set DATABASE_URL to jdbc:postgresql://HOST:5432/DATABASE (and DATABASE_USERNAME, DATABASE_PASSWORD)
  - Set PAYDECK_PUBLIC_BASE_URL to the API's own https:// address
	at dev.paydeck.api.common.ProductionSettingsCheck.onApplicationEvent(ProductionSettingsCheck.java:31) ~[!/:0.0.1-SNAPSHOT]
	...
	at org.springframework.boot.SpringApplication.prepareEnvironment(SpringApplication.java:356) ~[spring-boot-4.1.1.jar!/:4.1.1]
```

All three problems, in one go, and the stack trace shows where: `prepareEnvironment`, the first thing `SpringApplication.run` does. Nothing has tried the database.

### The tests

`ProductionSettingsCheckTest.java` now starts from a server that is ready and breaks one thing at a time:

```java
package dev.paydeck.api.common;

import static org.assertj.core.api.Assertions.assertThat;

import java.util.Map;

import org.junit.jupiter.api.Test;

class ProductionSettingsCheckTest {

    private static final Map<String, String> READY = Map.of(
            "JWT_SECRET", "q8Zt3nY1kVb0pLr7sXw2mCf9hJd4gTa6eUo5iRy",
            "DATABASE_URL", "jdbc:postgresql://db.internal:5432/paydeck",
            "PAYDECK_PUBLIC_BASE_URL", "https://api.paydeck.example");

    @Test
    void acceptsAServerThatIsReady() {
        assertThat(ProductionSettingsCheck.problems(READY::get)).isEmpty();
    }

    @Test
    void listsEverythingThatIsMissing() {
        assertThat(ProductionSettingsCheck.problems(name -> null)).hasSize(3);
    }

    @Test
    void refusesAShortSecret() {
        assertThat(ProductionSettingsCheck.problems(with("JWT_SECRET", "too-short")::get))
                .singleElement().asString().contains("JWT_SECRET");
    }

    @Test
    void refusesAPlainHttpAddress() {
        assertThat(ProductionSettingsCheck.problems(with("PAYDECK_PUBLIC_BASE_URL", "http://203.0.113.7:8080")::get))
                .singleElement().asString().contains("https://");
    }

    private static Map<String, String> with(String name, String value) {
        Map<String, String> settings = new java.util.HashMap<>(READY);
        settings.put(name, value);
        return settings;
    }
}
```

`with` copies the ready settings and changes one, so each test shows only what it is about (like `payment(changes)` in the app's tests, lesson 35.1). `singleElement()` also proves that the one bad setting caused exactly one problem, not three. `./mvnw test`: 118 tests, all green.

### Where each secret lives

| Secret | On your Mac | On the server | In GitHub |
|---|---|---|---|
| `JWT_SECRET` | the default in `application.yml` (fine: it only signs your own test tokens) | `.env`, made there | never |
| Database password | `paydeck`, in `docker-compose.yml` | `.env`, made there | never |
| Stripe and Google keys | your Mac's `.env` | `.env`, the server's own keys | never |
| Android upload key (lesson 36.4) | your home folder | not needed | an Actions secret |

Nothing in the table goes in the repository, and nothing goes in the image.

## Common mistakes

<Aside type="caution" title="Copying your Mac's .env to the server">
Then the server uses your test keys and a `JWT_SECRET` that has been on your laptop. Make each server's secrets on that server.
</Aside>

<Aside type="caution" title="A check that runs after what it guards">
A settings check that is an ordinary bean may run after the database connection it is meant to explain. Check settings at `ApplicationEnvironmentPreparedEvent`, before anything starts.
</Aside>

<Aside type="caution" title="Secrets in a Compose file">
`environment: JWT_SECRET: abc...` in `compose.production.yaml` puts the secret in Git. Compose files hold names (`${DATABASE_PASSWORD:?...}`, `env_file: .env`); `.env` holds values.
</Aside>

## Recap

- `application.yml`: defaults for your Mac and the names of overriding variables. `application-production.yml`: shared, non-secret server settings. `.env`: secrets and per-server values, `chmod 600`, never committed.
- `.env.example` lists every setting a server needs, without values.
- `forward-headers-strategy: framework` lets the API behind Caddy know it is on `https://`.
- `ProductionSettingsCheck` listens for `ApplicationEnvironmentPreparedEvent`, registered in `main`, so it names every missing setting before anything else can fail.
