**Goal:** By the end of this lesson no secret of PayDeck's lives in its code or its Git history, your REST Client file reads your password from a file Git ignores, and the API refuses to start on a real server with the development signing key.

## Why it matters

PayDeck's code will be public on GitHub. That is fine: good security never depends on the code being secret. But a handful of **values** must stay secret, and the most common way they leak is someone committing them by accident. Automated scanners watch every public push on GitHub, so a key that is pushed can be found and abused within minutes, long before you notice. Deleting it in the next commit does not help: it is still in the history.

## The idea

### What is a secret?

A secret is a value that gives power to whoever knows it. PayDeck has these so far, and Part 9 adds more:

| Secret | What someone could do with it |
|--------|-------------------------------|
| `JWT_SECRET` | Sign their own access tokens, as anyone, including an admin (lesson 27.5) |
| Google client secret | Pretend to be PayDeck to Google |
| Database password | Read and change every balance directly |
| Passwords and tokens you use while testing | Sign in as that user |
| Stripe secret key and webhook secret (Module 31) | Take payments, refund them, fake payment events |

Not secrets: the Google **client ID** (it appears in every sign-in URL), account and card IDs, the API's address, the code. Treating everything as secret makes people careless with what really is.

### Where secrets should live

**In the environment, not in the code.** The code says which setting it needs, and the place it runs supplies the value:

- **On your Mac:** a `.env` file next to the code, listed in `.gitignore`, loaded with `source .env` (lesson 29.3).
- **On a real server:** the hosting service's settings for environment variables or secrets (Part 10).
- **In the code:** only a name, such as `${JWT_SECRET:...}` in `application.yml` (lesson 27.5). The default after the colon is a development value, and its text says so.

### Defaults are dangerous in production

That development default is convenient: the API starts on your Mac without any setup. On a real server, though, a forgotten `JWT_SECRET` means the API runs with a key printed in a public repository, and anyone can sign admin tokens. A misconfiguration (OWASP A02) that silently works is the worst kind. So the production profile should **refuse to start** until the real secret is set: a loud failure on deploy day beats a quiet breach later.

### When a secret leaks

If a secret reaches Git, or a screenshot, or a chat message:

1. **Rotate it**: make a new one and stop the old one working. For `JWT_SECRET`, that signs everyone out; for Google or Stripe, you create a new secret in their dashboard and delete the old one.
2. **Then** clean up: remove it from the code, and look for where else it went.

Rewriting Git history to remove the commit is not enough on its own. Anyone may have cloned or scanned it already. Rotation is the fix; cleaning up is tidying.

## Worked example

### Check what Git ignores

In the API folder, ask Git which rule ignores your `.env` files:

```sh
git check-ignore -v .env http/.env
```

```
.gitignore:5:.env	.env
.gitignore:5:.env	http/.env
```

The rule `.env` (with no `/`) matches a file of that name in **any** folder, so `http/.env` is ignored too. If this prints nothing for a file, Git would happily commit it.

### Your REST Client password

Since the Module 27 project, `http/paydeck.http` contains Asha's password in plain text. It is only a test password, but it is a bad habit, and the same file will soon hold real test accounts. REST Client can read values from a `.env` file in the same folder as the `.http` file. Create `http/.env`:

```sh
PAYDECK_EMAIL=asha@example.com
PAYDECK_PASSWORD=correct horse battery
```

and change the sign-in request to use it:

```http
### Sign in
# @name login
POST {{baseUrl}}/api/auth/login
Content-Type: application/json

{
  "email": "{{$dotenv PAYDECK_EMAIL}}",
  "password": "{{$dotenv PAYDECK_PASSWORD}}"
}
```

`{{$dotenv NAME}}` is replaced by `NAME`'s value from that file when you send the request. The `.http` file can now be committed and shared: everyone puts their own test user in their own `.env`. A file like `http/.env.example` with the names and fake values is a friendly way to tell teammates what to fill in.

### Refuse to start with the development key

`src/main/java/dev/paydeck/api/common/ProductionSettingsCheck.java`:

```java
package dev.paydeck.api.common;

import java.util.ArrayList;
import java.util.List;
import java.util.function.Function;

import org.springframework.context.annotation.Profile;
import org.springframework.core.env.Environment;
import org.springframework.stereotype.Component;

/**
 * Refuses to start a deployed API that still has the settings meant for your
 * own Mac. Runs only with {@code SPRING_PROFILES_ACTIVE=production}: a clear
 * message at start-up beats a guessable signing key later.
 */
@Component
@Profile("production")
public class ProductionSettingsCheck {

    public ProductionSettingsCheck(Environment environment) {
        List<String> problems = problems(environment::getProperty);
        if (!problems.isEmpty()) {
            throw new IllegalStateException("PayDeck is not ready for production:\n  - "
                    + String.join("\n  - ", problems));
        }
    }

    /** Each problem as a sentence. {@code settings} reads an environment variable. */
    public static List<String> problems(Function<String, String> settings) {
        List<String> problems = new ArrayList<>();
        String secret = settings.apply("JWT_SECRET");
        if (secret == null || secret.length() < 32) {
            problems.add("Set JWT_SECRET to a long random value, for example from: openssl rand -base64 48");
        }
        return problems;
    }
}
```

How it fits together:

- `@Profile("production")` means Spring only creates this bean when the `production` profile is active (lesson 21.4). On your Mac it does not exist.
- Spring creates beans while the application starts, so an exception in the constructor stops the start-up, with the message on screen.
- The rule itself is in a `static` method that takes "a way to look up a setting" (a `Function<String, String>`), not Spring's `Environment`. In production it is given `environment::getProperty`; in a test, a `Map`'s `get` (method references, lesson 17.4). So it can be tested without starting anything.
- It returns a **list** of problems. Part 10 adds more checks (the database address, the API's public address), and a list means one failed start tells you everything that is missing, not one thing at a time.

`src/test/java/dev/paydeck/api/common/ProductionSettingsCheckTest.java`:

```java
package dev.paydeck.api.common;

import static org.assertj.core.api.Assertions.assertThat;

import java.util.Map;

import org.junit.jupiter.api.Test;

class ProductionSettingsCheckTest {

    @Test
    void acceptsALongRandomSecret() {
        Map<String, String> settings = Map.of("JWT_SECRET", "q8Zt3nY1kVb0pLr7sXw2mCf9hJd4gTa6eUo5iRy");
        assertThat(ProductionSettingsCheck.problems(settings::get)).isEmpty();
    }

    @Test
    void refusesAMissingSecret() {
        assertThat(ProductionSettingsCheck.problems(name -> null)).singleElement()
                .asString().contains("JWT_SECRET");
    }

    @Test
    void refusesAShortSecret() {
        Map<String, String> settings = Map.of("JWT_SECRET", "too-short");
        assertThat(ProductionSettingsCheck.problems(settings::get)).hasSize(1);
    }
}
```

The "long random secret" in the test is not a real one: it only has to be long. `./mvnw test`: 78 tests, all green.

### Try it

Start the API as a real server would, with the production profile and no secret. `SERVER_PORT=8081` keeps it away from the API you already have running:

```sh
SERVER_PORT=8081 SPRING_PROFILES_ACTIVE=production ./mvnw spring-boot:run
```

It stops after a few seconds. Among the long error output:

```
Caused by: java.lang.IllegalStateException: PayDeck is not ready for production:
  - Set JWT_SECRET to a long random value, for example from: openssl rand -base64 48
```

Now with a real secret, made fresh by `openssl`:

```sh
SERVER_PORT=8081 SPRING_PROFILES_ACTIVE=production JWT_SECRET="$(openssl rand -base64 48)" ./mvnw spring-boot:run
```

```
Started PayDeckApplication in 8.66 seconds (process running for 9.013)
```

In another terminal:

```sh
curl -s localhost:8081/actuator/health
```

```json
{"groups":["liveness","readiness"],"status":"UP"}
```

Production mode also hides the health details (from the Module 21 project). Stop it with Ctrl+C. The secret was never written anywhere: it existed only in that one command's environment. On a real server it will come from the host's secret settings.

### Search the history

`git log -S` finds every commit that added or removed a piece of text. Look for the development default:

```sh
git log -S "change-me" --oneline
```

```
daed5e4 27.5 jwt
```

That is fine: it is the default, meant to be public. Now search for something that must never be there. Google client secrets start with `GOCSPX`:

```sh
git log -S "GOCSPX" --oneline
```

No output: no commit ever contained one. Your commit IDs and messages will be your own.

GitHub also scans public repositories for well-known secret formats, including Google and Stripe keys, and can block a push that contains one ("push protection"). Treat that as a safety net, not a plan.

You realise that yesterday you ran `git add .` and pushed a commit that included `.env`, with the Google client secret and a database password, before `.env` was in `.gitignore`. Write down, in order, what you do. Then check your own repository: run `git log --all --oneline -- .env http/.env`. What does it print?

<Fragment slot="hint">Which matters more: removing the file from GitHub, or making the leaked values useless? The `--` in `git log` limits it to commits that touched those paths.</Fragment>
<Fragment slot="solution">

1. **Rotate first.** In the Google Cloud console, create a new client secret for PayDeck's client and delete the old one. Change the database password. Put the new values in your (ignored) `.env`, and restart the API.
2. **Stop it happening again**: add `.env` to `.gitignore`, `git rm --cached .env` (removes it from Git but keeps your file), and commit.
3. **Look for damage**: Google's console and the database logs show unexpected use. In PayDeck, the audit log shows unusual sign-ins.
4. Optionally rewrite history to remove the file. That is tidying only: the old values are already useless after step 1.

In a repository that followed this course, `git log --all --oneline -- .env http/.env` prints nothing: no commit ever touched those files.

## Common mistakes

<Aside type="caution" title="Putting secrets in the app">
Anything inside the React Native app can be read by anyone who downloads it, as lesson 29.1 said about the client secret. The app has no secrets; the API holds them.
</Aside>

<Aside type="caution" title="Deleting the secret in a new commit and moving on">
The old commit still contains it, and so does every clone and fork. Rotate.
</Aside>

<Aside type="caution" title="Printing secrets in logs">
`log.info("Starting with secret {}", secret)` puts it in every log file and every log service. Log that a setting is present, never its value.
</Aside>

## Recap

- A secret gives power to whoever knows it; IDs, client IDs and the code are not secrets.
- Secrets come from the environment: `.env` on your Mac (ignored by Git), the host's settings on a server, and only names in the code.
- `{{$dotenv NAME}}` keeps test passwords out of `.http` files.
- `ProductionSettingsCheck` refuses to start the production profile with a missing or short `JWT_SECRET`.
- `git log -S` searches history. If a secret leaks, **rotate it first**.
