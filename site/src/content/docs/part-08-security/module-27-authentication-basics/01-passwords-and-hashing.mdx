**Goal:** By the end of this lesson you can explain how a website checks a password without storing it, and you have seen BCrypt, the algorithm PayDeck will use, at work in your own project.

## Why it matters

Until now, anyone who knew an account's ID could see its balance and move its money. Part 8 fixes that: people sign up with an email and a password, and only they can use their accounts. The first question is the most important one: **what do we keep in the database so we can check a password later?**

The obvious answer, the password itself, is a disaster waiting to happen. Databases leak: through a bug, a stolen laptop, a careless backup, a dishonest employee. Most people reuse passwords, so a leaked list of PayDeck passwords also unlocks their email and their bank. Every few months the news has another company that stored passwords badly. PayDeck will not be one of them.

## The idea

### A hash: a fingerprint you cannot reverse

A **hash function** turns any text into a fixed-length code, its **hash**. You met one in lesson 24.5: SHA-256, which PayDeck uses to fingerprint requests. A hash function has three properties that make it useful for passwords:

1. **The same input always gives the same hash.** So when someone signs in, we hash what they typed and compare it with the stored hash.
2. **A tiny change gives a completely different hash.** `sunshine123` and `sunshine124` look nothing alike once hashed.
3. **It only works one way.** There is no "unhash": from the hash you cannot work out the password.

So PayDeck stores the hash, and checks a sign-in by hashing what was typed. The password itself is never saved anywhere.

### Why SHA-256 is not enough

If you cannot reverse a hash, how do attackers get passwords out of a leaked database? They **guess**. They take a list of common passwords (`123456`, `password`, `sunshine123`, ...) and every word in every dictionary, hash each one, and look for matches. SHA-256 was designed to be **fast**, which is exactly wrong here: you will see in a moment that an ordinary laptop computes a million SHA-256 hashes in under a second. A gaming graphics card does billions.

There is a second problem. Because the same password always gives the same hash, everyone with `sunshine123` has the same hash. One guess cracks all of them at once, and attackers can even prepare giant tables of hashes in advance.

### BCrypt: salted and slow on purpose

Password hashing algorithms fix both problems. PayDeck uses **BCrypt**, which has been the standard choice for over twenty years:

- **A salt.** Before hashing, BCrypt adds a random value, the **salt**, different for every password, and stores it inside the result. Two people with the same password get different hashes, so every guess has to be tried against every user separately, and tables prepared in advance are useless.
- **Slow on purpose.** BCrypt repeats its work many times. How many is set by its **cost**: cost 10 means 2¹⁰ = 1,024 rounds. One sign-in takes a fraction of a second, which nobody notices. But an attacker who could try a billion SHA-256 guesses now manages only thousands of BCrypt guesses in the same time.

A BCrypt hash looks like this, and contains everything needed to check a password later:

```
$2a$10$OWzCqTOlSwz7hmUuFCIqEOCj61maSTgKbe7wPhnjmDywGNYKtzOXm
 │  │  └─ salt (22 characters), then the hash itself (31 characters)
 │  └─ cost: 2¹⁰ rounds
 └─ the BCrypt version
```

### Never invent your own

Security code fails silently: a homemade scheme works perfectly in every test and is cracked in an afternoon by someone who knows the tricks. Use the well-known algorithm, from a well-known library. For PayDeck, that library is **Spring Security**, which you add properly in lesson 27.3. For now you only need its small `spring-security-crypto` part.

## Worked example

### Add the library

In the API project, `~/Projects/course/paydeck-api`, add to the `<dependencies>` in `pom.xml`, next to the other dependencies:

```xml
<dependency>
    <groupId>org.springframework.security</groupId>
    <artifactId>spring-security-crypto</artifactId>
</dependency>
```

There is no `<version>`: Spring Boot chooses the one that matches it, as for the starters (lesson 21.2).

### A test to watch hashing

You will not use this code in PayDeck itself. A test is simply a convenient place to run some Java and look at the results. Create `src/test/java/dev/paydeck/api/auth/PasswordHashingTest.java`:

```java
package dev.paydeck.api.auth;

import static org.assertj.core.api.Assertions.assertThat;

import java.nio.charset.StandardCharsets;
import java.security.MessageDigest;
import java.util.HexFormat;

import org.junit.jupiter.api.Test;
import org.springframework.security.crypto.factory.PasswordEncoderFactories;
import org.springframework.security.crypto.password.PasswordEncoder;

/** Not a test of PayDeck: a place to see how password hashing behaves. */
class PasswordHashingTest {

    private final PasswordEncoder encoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();

    @Test
    void sha256IsFastAndAlwaysTheSame() throws Exception {
        MessageDigest sha256 = MessageDigest.getInstance("SHA-256");
        String first = HexFormat.of().formatHex(sha256.digest("sunshine123".getBytes(StandardCharsets.UTF_8)));
        String second = HexFormat.of().formatHex(sha256.digest("sunshine123".getBytes(StandardCharsets.UTF_8)));
        System.out.println("SHA-256: " + first);
        System.out.println("again:   " + second);
        assertThat(first).isEqualTo(second);

        long start = System.nanoTime();
        for (int i = 0; i < 1_000_000; i++) {
            sha256.digest(("guess" + i).getBytes(StandardCharsets.UTF_8));
        }
        System.out.printf("1,000,000 SHA-256 hashes took %d ms%n", (System.nanoTime() - start) / 1_000_000);
    }

    @Test
    void bcryptIsSaltedAndSlow() {
        String first = encoder.encode("sunshine123");
        String second = encoder.encode("sunshine123");
        System.out.println("BCrypt: " + first);
        System.out.println("again:  " + second);
        assertThat(first).isNotEqualTo(second);

        assertThat(encoder.matches("sunshine123", first)).isTrue();
        assertThat(encoder.matches("sunshine124", first)).isFalse();

        long start = System.nanoTime();
        for (int i = 0; i < 10; i++) {
            encoder.encode("guess" + i);
        }
        System.out.printf("10 BCrypt hashes took %d ms%n", (System.nanoTime() - start) / 1_000_000);
    }
}
```

- **`PasswordEncoder`** is Spring Security's interface for password hashing, with two methods: `encode(password)` makes a hash, `matches(typed, storedHash)` checks a password against one. You never compare hashes with `equals` yourself: with a salt, that would never match.
- **`PasswordEncoderFactories.createDelegatingPasswordEncoder()`** gives an encoder that uses BCrypt and writes `{bcrypt}` in front of each hash. That label says which algorithm made it, so if PayDeck ever moves to a newer algorithm, old hashes still work and new ones use the new one.
- **`System.nanoTime()`** reads a very precise clock, in nanoseconds. Subtracting two readings and dividing by a million gives milliseconds.
- **`HexFormat.of().formatHex(...)`** writes the 32 bytes of a SHA-256 hash as 64 hexadecimal characters.

Run it:

```sh
./mvnw test -Dtest=PasswordHashingTest
```

`-Dtest=` runs only that test class. Among Maven's output:

```
SHA-256: 816a4092660e4e87b5b584c4a51e7b33db2fb1b8f972578ef90c5ed7608e0f19
again:   816a4092660e4e87b5b584c4a51e7b33db2fb1b8f972578ef90c5ed7608e0f19
1,000,000 SHA-256 hashes took 457 ms
BCrypt: {bcrypt}$2a$10$OWzCqTOlSwz7hmUuFCIqEOCj61maSTgKbe7wPhnjmDywGNYKtzOXm
again:  {bcrypt}$2a$10$KLZjd0jn0vFxufPpiX2/EuTUE5TttDdz85XAZZWvSRj6zS2SCfzqi
10 BCrypt hashes took 740 ms
```

Your hashes and times will differ, but the pattern will not:

- SHA-256 gave the **same** hash twice. BCrypt gave **different** hashes for the same password (different salts), and `matches` still recognised the right password and refused the wrong one.
- One SHA-256 hash took about half a **microsecond** (a millionth of a second). One BCrypt hash took about 74 **milliseconds**: roughly 150,000 times slower. To you, signing in, 74 ms is nothing. To an attacker trying a list of a billion passwords against one user, it is the difference between minutes and centuries.

```java
package dev.paydeck.api.auth;

import org.junit.jupiter.api.Test;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;

class BcryptCostTest {

    @Test
    void costChangesTheTime() {
        for (int cost : new int[] {10, 11, 12, 13}) {
            BCryptPasswordEncoder encoder = new BCryptPasswordEncoder(cost);
            long start = System.nanoTime();
            String hash = encoder.encode("sunshine123");
            System.out.printf("cost %d: %4d ms  %s%n", cost, (System.nanoTime() - start) / 1_000_000, hash);
        }
    }
}
```

## Common mistakes

<Aside type="caution" title="Encrypting instead of hashing">
Encryption can be reversed by anyone with the key, and the key has to live somewhere near the database. Hashing has no key and cannot be reversed. Passwords are hashed, never encrypted.
</Aside>

<Aside type="caution" title="Comparing hashes with equals">
`encoder.encode(typed).equals(storedHash)` is always `false` with BCrypt, because the new hash has a new salt. Always use `encoder.matches(typed, storedHash)`, which reads the salt from the stored hash.
</Aside>

<Aside type="caution" title="Logging passwords">
A password that is hashed in the database but printed in a log file is not protected at all. Never log a request body that contains a password, and never put a password in a URL, where servers and proxies log it.
</Aside>

<Aside type="caution" title="Limiting passwords to 8 characters">
Length helps far more than odd symbols. PayDeck will ask for at least 10 characters and allow long phrases like `correct horse battery`, which are easy to remember and hard to guess.
</Aside>

## Recap

- Never store passwords. Store a hash, and check a sign-in by comparing hashes.
- A hash is one-way: the same input gives the same output, and the output cannot be turned back.
- Fast hashes like SHA-256 are wrong for passwords; attackers can guess billions per second.
- BCrypt adds a random salt to every password and is slow on purpose; its cost doubles the work per step.
- Use `PasswordEncoder.encode` and `matches` from Spring Security, never your own scheme.
