PayDeck now keeps its accounts and cards in PostgreSQL, in tables your own migration created. In this project you make sure it all holds together, the way you would before showing it to anyone: you prove the data lasts, prove the rules hold, update the try-it file for the new URLs, and write the kind of report someone running PayDeck would ask for.

## The tasks

1. **Try-it file.** Rename `http/cards.http` to `http/paydeck.http` and rewrite it for the new URLs: open an account, read it, issue two cards under it (one with a limit, one without), list the account's cards, then rename, freeze, unfreeze and cancel one card. Add one request for each of these errors: a currency PayDeck does not support (`400`), an account that does not exist (`404`), and a cancelled card that cannot be renamed (`422`).
2. **System accounts are invisible.** Show, with two requests, that the API acts as if the USD system account `00000000-0000-0000-0000-000000000840` does not exist: reading it answers `404`, and issuing a card for it answers `404`.
3. **Data survives a restart.** Freeze a card, stop the API, start it again, and list the account's cards. The card must still be `FROZEN`.
4. **A report in SQL.** In psql, list every customer account with its owner's name, its currency, how many `ACTIVE` cards it has and how many cards in total. Accounts with no cards must appear, with `0`.
5. **Tests need the database.** Stop the database (`docker compose stop`) and run `./mvnw test`. Read why it fails. Start the database again (`docker compose start`) and run the tests until all 7 pass.
6. Commit.

<Fragment slot="hint">For task 4, you need every account, even those without a match in `cards`: that is a `LEFT JOIN` from `accounts`. To count only some rows inside a group, PostgreSQL has `count(c.id) FILTER (WHERE c.status = 'ACTIVE')`. Counting `c.id` instead of `*` gives `0` for an account with no cards, because the joined `c.id` is `NULL`.</Fragment>

The row is in the database, but `.filter(a -> a.getKind() == AccountKind.CUSTOMER)` makes the API treat it as missing. Answering `404` rather than `403 Forbidden` is deliberate: it does not even admit that the account exists.

Task 4:

```sql
SELECT a.owner_name,
       a.currency,
       count(c.id) FILTER (WHERE c.status = 'ACTIVE') AS active_cards,
       count(c.id) AS all_cards
FROM accounts a
LEFT JOIN cards c ON c.account_id = a.id
WHERE a.kind = 'CUSTOMER'
GROUP BY a.id, a.owner_name, a.currency
ORDER BY a.owner_name;
```

```
 owner_name | currency | active_cards | all_cards
------------+----------+--------------+-----------
 Ana Silva  | USD      |            1 |         2
 Ben Okafor | EUR      |            0 |         0
(2 rows)
```

`GROUP BY a.id` (not only the name) keeps two customers with the same name apart.

What to notice:

- **Tests that depend on your laptop are fragile.** They fail when you forget to start Docker, and they read and write your practice data. Module 25 fixes both: each test run starts its own throwaway PostgreSQL.
- **Rules in two places.** The API refuses a system account, and the database refuses a second system account per currency. Each protects against things the other cannot see.
- **The four system accounts are waiting.** No customer can see them yet, but in Module 24 every top-up moves money from one of them into a customer's account.
