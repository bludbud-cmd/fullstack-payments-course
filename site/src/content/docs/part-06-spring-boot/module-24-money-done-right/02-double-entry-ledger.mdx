**Goal:** By the end of this lesson PayDeck records money in a double-entry ledger, works out each account's balance from it, and lets you top up an account through the API.

## Why it matters

The obvious way to store a balance is a `balance_cents` column that you add to and subtract from. It works until the day a customer asks "why is my balance $12 lower than I expected?" and all you have is a number. It also lets a single bug create money from nothing, and nobody would notice. Banks solved this more than 500 years ago with **double-entry bookkeeping**, and every serious payment system still uses it.

## The idea

### Entries, not balances

You saw the idea in Module 1: instead of storing a balance, store every change, and add them up. PayDeck has two tables:

- **`ledger_transactions`**: one row per movement of money ("Ana topped up $50.00").
- **`ledger_entries`**: the lines of each transaction. Each entry says "this account, plus or minus this many cents".

An account's balance is the sum of its entries. It is never stored, so it can never disagree with the history.

### Double entry

The rule that makes it *double* entry: **the entries of every transaction add up to zero.** Money is never created or destroyed; it only moves. If Ana sends Ben $10:

| Account | Amount (cents) |
| --- | --- |
| Ana | −1000 |
| Ben | +1000 |
| **Total** | **0** |

But when Ana tops up her account from her bank card, where does the money come from? From outside PayDeck. That is what the four `SYSTEM` accounts from lesson 23.4 are for. A top-up of $50.00:

| Account | Amount (cents) |
| --- | --- |
| Outside world (USD) | −5000 |
| Ana | +5000 |
| **Total** | **0** |

The "Outside world" account goes negative, and its balance is always minus the total of money that has come into PayDeck. Add up **every entry in the whole ledger** and you always get 0. If you ever do not, there is a bug, and you know immediately.

## Worked example

### The tables

Create `src/main/resources/db/migration/V2__create_ledger.sql`:

```sql
-- Every movement of money is one ledger transaction made of two or more
-- entries whose amounts add up to zero (double-entry bookkeeping).
-- A balance is never stored: it is the sum of an account's entries.
CREATE TABLE ledger_transactions (
    id                   UUID PRIMARY KEY,
    type                 VARCHAR(20)  NOT NULL CHECK (type IN ('TOP_UP', 'TRANSFER')),
    description          VARCHAR(140) NOT NULL,
    -- The same Idempotency-Key always means the same request, so a retry
    -- can never move money twice.
    idempotency_key      VARCHAR(100) NOT NULL UNIQUE,
    request_fingerprint  VARCHAR(64)  NOT NULL,
    created_at           TIMESTAMPTZ  NOT NULL
);

CREATE TABLE ledger_entries (
    id              UUID PRIMARY KEY,
    transaction_id  UUID    NOT NULL REFERENCES ledger_transactions (id),
    account_id      UUID    NOT NULL REFERENCES accounts (id),
    amount_cents    BIGINT  NOT NULL CHECK (amount_cents <> 0)
);

CREATE INDEX ledger_entries_account_id ON ledger_entries (account_id);
CREATE INDEX ledger_entries_transaction_id ON ledger_entries (transaction_id);
```

`idempotency_key` and `request_fingerprint` stop a payment from happening twice when a phone retries a request. Lesson 24.5 explains them; they are here now because a migration, once applied, never changes. `<>` means "not equal": an entry of 0 cents is meaningless.

Notice what is **not** there: no `UPDATE` will ever touch these tables. A ledger only grows. To undo a payment, you add a new transaction that moves the money back, so the history shows both.

`LedgerTransaction.java`. It owns its entries: `@OneToMany(mappedBy = "transaction", cascade = CascadeType.PERSIST)` means "the entries point back at me through their `transaction` field, and when I am saved, save them too":

```java
package dev.paydeck.api.ledger;

import java.time.Instant;
import java.util.ArrayList;
import java.util.List;
import java.util.UUID;

import jakarta.persistence.CascadeType;
import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.EnumType;
import jakarta.persistence.Enumerated;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.OneToMany;
import jakarta.persistence.Table;

/** One movement of money, made of entries that always add up to zero. */
@Entity
@Table(name = "ledger_transactions")
public class LedgerTransaction {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private TransactionType type;

    @Column(nullable = false)
    private String description;

    @Column(nullable = false, unique = true)
    private String idempotencyKey;

    @Column(nullable = false)
    private String requestFingerprint;

    @Column(nullable = false)
    private Instant createdAt;

    @OneToMany(mappedBy = "transaction", cascade = CascadeType.PERSIST)
    private List<LedgerEntry> entries = new ArrayList<>();

    protected LedgerTransaction() {
        // For JPA
    }

    LedgerTransaction(TransactionType type, String description, String idempotencyKey, String requestFingerprint) {
        this.type = type;
        this.description = description;
        this.idempotencyKey = idempotencyKey;
        this.requestFingerprint = requestFingerprint;
        this.createdAt = Instant.now();
    }

    void addEntry(UUID accountId, long amountCents) {
        entries.add(new LedgerEntry(this, accountId, amountCents));
    }

    public UUID getId() {
        return id;
    }

    public TransactionType getType() {
        return type;
    }

    public String getDescription() {
        return description;
    }

    public String getRequestFingerprint() {
        return requestFingerprint;
    }

    public Instant getCreatedAt() {
        return createdAt;
    }

    public List<LedgerEntry> getEntries() {
        return List.copyOf(entries);
    }
}
```

The constructor and `addEntry` have no `public`: only classes in the `ledger` package can use them. Code elsewhere cannot build a transaction by hand; it has to ask `LedgerService`, which checks the rules. `getEntries` hands out a copy, so nobody can add an entry to the list from outside either.

`LedgerEntry.java`. This is the first `@ManyToOne` you write (lesson 23.3 explained why cards use a plain `accountId` instead): an entry belongs to one transaction, and is meaningless without it. Its account stays a plain ID, like a card's.

```java
package dev.paydeck.api.ledger;

import java.util.UUID;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.Table;

/** One line of a ledger transaction: money into (positive) or out of (negative) one account. */
@Entity
@Table(name = "ledger_entries")
public class LedgerEntry {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "transaction_id")
    private LedgerTransaction transaction;

    @Column(nullable = false)
    private UUID accountId;

    @Column(nullable = false)
    private long amountCents;

    protected LedgerEntry() {
        // For JPA
    }

    LedgerEntry(LedgerTransaction transaction, UUID accountId, long amountCents) {
        this.transaction = transaction;
        this.accountId = accountId;
        this.amountCents = amountCents;
    }

    public UUID getAccountId() {
        return accountId;
    }

    public long getAmountCents() {
        return amountCents;
    }
}
```

The two repositories. The balance is a query with **`@Query`**, which lets you write the query yourself when a method name cannot say it. The language is **JPQL**: it looks like SQL but uses entity and field names (`LedgerEntry`, `amountCents`) instead of table and column names. `coalesce(..., 0)` turns "no entries" (`NULL`) into 0.

And `LedgerService.java`, the **only** place where money is recorded. It refuses anything that does not balance:

```java
package dev.paydeck.api.ledger;

import java.util.List;
import java.util.UUID;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/**
 * The only way money moves in PayDeck. Every transaction must balance:
 * whatever leaves one account arrives in another, so money is never created
 * or lost by accident.
 */
@Service
public class LedgerService {

    private final LedgerTransactionRepository transactions;
    private final LedgerEntryRepository entries;

    public LedgerService(LedgerTransactionRepository transactions, LedgerEntryRepository entries) {
        this.transactions = transactions;
        this.entries = entries;
    }

    @Transactional
    public LedgerTransaction record(TransactionType type, String description, String idempotencyKey,
                                    String requestFingerprint, List<Posting> postings) {
        checkBalanced(postings);
        LedgerTransaction transaction = new LedgerTransaction(type, description, idempotencyKey, requestFingerprint);
        postings.forEach(posting -> transaction.addEntry(posting.accountId(), posting.amountCents()));
        return transactions.save(transaction);
    }

    static void checkBalanced(List<Posting> postings) {
        if (postings.size() < 2) {
            throw new IllegalArgumentException("A transaction needs at least two postings");
        }
        if (postings.stream().anyMatch(posting -> posting.amountCents() == 0)) {
            throw new IllegalArgumentException("A posting cannot be zero");
        }
        long total = postings.stream().mapToLong(Posting::amountCents).reduce(0, Math::addExact);
        if (total != 0) {
            throw new IllegalArgumentException("Postings must add up to zero but add up to " + total);
        }
    }

    @Transactional(readOnly = true)
    public long balanceOf(UUID accountId) {
        return entries.sumByAccountId(accountId);
    }
}
```

`@Service` is like `@Component` (Module 21): Spring creates one and injects it, and the name says "business logic lives here". `reduce(0, Math::addExact)` adds the amounts up, throwing on overflow instead of wrapping around (lesson 24.1). The check throws `IllegalArgumentException`, which becomes a `500`: an unbalanced transaction is never the customer's fault, it is a bug in PayDeck, and it must stop everything.

`MoneyMovementService.java` decides *what* to record:

```java
package dev.paydeck.api.money;

import java.util.List;
import java.util.UUID;

import dev.paydeck.api.account.Account;
import dev.paydeck.api.account.AccountKind;
import dev.paydeck.api.account.AccountRepository;
import dev.paydeck.api.common.NotFoundException;
import dev.paydeck.api.ledger.LedgerService;
import dev.paydeck.api.ledger.LedgerTransaction;
import dev.paydeck.api.ledger.Posting;
import dev.paydeck.api.ledger.TransactionType;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

/** Tops up and transfers money, always as one balanced ledger transaction. */
@Service
public class MoneyMovementService {

    private final AccountRepository accounts;
    private final LedgerService ledger;

    public MoneyMovementService(AccountRepository accounts, LedgerService ledger) {
        this.accounts = accounts;
        this.ledger = ledger;
    }

    @Transactional
    public LedgerTransaction topUp(UUID accountId, long amountCents, String description) {
        Account account = customerAccount(accountId);
        Account outsideWorld = accounts.findByKindAndCurrency(AccountKind.SYSTEM, account.getCurrency())
                .orElseThrow(() -> new IllegalStateException("No system account for " + account.getCurrency()));
        // Lesson 24.5 replaces these two placeholders.
        String idempotencyKey = UUID.randomUUID().toString();
        String fingerprint = "-";
        return ledger.record(TransactionType.TOP_UP, description, idempotencyKey, fingerprint,
                List.of(new Posting(outsideWorld.getId(), -amountCents), new Posting(account.getId(), amountCents)));
    }

    private Account customerAccount(UUID id) {
        return accounts.findById(id)
                .filter(account -> account.getKind() == AccountKind.CUSTOMER)
                .orElseThrow(() -> new NotFoundException("Account", id));
    }
}
```

In PayDeck's real app, a top-up comes from a bank card through Stripe (Module 31). Until then, this one simply believes the customer: it is a pretend top-up, which is exactly what you need to test everything else.

`MoneyController.java` (with the same `@Max` limit as cards, $100,000.00):

```java
package dev.paydeck.api.money;

import java.time.Instant;
import java.util.UUID;

import dev.paydeck.api.ledger.LedgerTransaction;
import dev.paydeck.api.ledger.TransactionType;
import jakarta.validation.Valid;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.Positive;
import jakarta.validation.constraints.Size;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class MoneyController {

    /** The most a single top-up or transfer can move: 100,000.00 in the account's currency. */
    static final long MAX_AMOUNT_CENTS = 10_000_000;

    public record TopUpRequest(
            @Positive @Max(MAX_AMOUNT_CENTS) long amountCents,
            @NotBlank @Size(max = 140) String description) {
    }

    public record TransactionResponse(
            UUID id, TransactionType type, String description, long amountCents, Instant createdAt) {
    }

    private final MoneyMovementService money;

    public MoneyController(MoneyMovementService money) {
        this.money = money;
    }

    @PostMapping("/api/accounts/{accountId}/top-ups")
    public ResponseEntity<TransactionResponse> topUp(@PathVariable UUID accountId,
                                                     @Valid @RequestBody TopUpRequest request) {
        LedgerTransaction transaction = money.topUp(accountId, request.amountCents(), request.description().strip());
        return ResponseEntity.status(HttpStatus.CREATED).body(new TransactionResponse(transaction.getId(),
                transaction.getType(), transaction.getDescription(), request.amountCents(), transaction.getCreatedAt()));
    }
}
```

Here `amountCents` is a `long`, not a `Long`, on purpose. A request with no amount at all is refused with a plain `400`, because Jackson will not put "nothing" into a `long` (lesson 22.2's `Boolean` problem, this time working for you). `@Positive` refuses `0` and negative amounts, so nobody can "top up" money out of an account.

Finally, show the balance on an account. In `AccountController`, inject `LedgerService` and add `balanceCents` to the response:

```java
public record AccountResponse(
        UUID id, String ownerName, SupportedCurrency currency, long balanceCents, Instant createdAt) {
}

private final AccountRepository accounts;
private final LedgerService ledger;

public AccountController(AccountRepository accounts, LedgerService ledger) {
    this.accounts = accounts;
    this.ledger = ledger;
}

@PostMapping
@Transactional
public ResponseEntity<AccountResponse> open(@Valid @RequestBody OpenAccountRequest request) {
    Account account = accounts.save(Account.openCustomerAccount(request.ownerName().strip(), request.currency()));
    return ResponseEntity.created(URI.create("/api/accounts/" + account.getId()))
            .body(toResponse(account, 0));
}

@GetMapping("/{id}")
@Transactional(readOnly = true)
public AccountResponse get(@PathVariable UUID id) {
    Account account = accounts.findById(id)
            .filter(a -> a.getKind() == AccountKind.CUSTOMER)
            .orElseThrow(() -> new NotFoundException("Account", id));
    return toResponse(account, ledger.balanceOf(id));
}

private static AccountResponse toResponse(Account account, long balanceCents) {
    return new AccountResponse(account.getId(), account.getOwnerName(), account.getCurrency(),
            balanceCents, account.getCreatedAt());
}
```

A new account's balance is 0 without asking: it cannot have entries yet.

## Common mistakes

<Aside type="caution" title="Storing a balance column as well">
It looks like a harmless shortcut, but now there are two truths that can disagree. If a balance query ever gets slow, the fix comes later and is carefully checked against the ledger; it never replaces it.
</Aside>

<Aside type="caution" title="Updating or deleting ledger rows">
A mistaken payment is corrected with a new transaction that reverses it. Editing history destroys the very record that explains a balance.
</Aside>

<Aside type="caution" title="Topping up a system account">
`customerAccount` refuses it with `404`. A top-up into the outside world would be money moving from the outside world to the outside world.
</Aside>

## Recap

- A ledger stores every movement of money; balances are sums of entries, never stored.
- Double entry: the entries of each transaction add up to zero, so the whole ledger always does.
- Money entering PayDeck comes from a `SYSTEM` "outside world" account, which goes negative.
- `LedgerService` is the only way to record money, and it refuses unbalanced transactions.
- `@Query` with JPQL lets you write queries that method names cannot, such as a sum.
