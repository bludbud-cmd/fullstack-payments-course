**Goal:** By the end of this lesson you can read a database table, and explain why a payments app records every movement of money.

## Why it matters

A server forgets everything when it restarts, just like memory forgets when the power goes off. Everything PayDeck must remember (people, accounts, cards, every payment) lives in a **database**. In Part 5 you will write database queries, and in Part 6 the PayDeck API will use a database called **PostgreSQL**.

## The idea

A **database** is a program whose whole job is storing data safely and finding it again quickly. Most databases you will meet organise data into **tables**, like spreadsheets:

**cards**

| id | account_id | nickname | last4 | status |
| --- | --- | --- | --- | --- |
| 7 | 42 | Everyday | 4242 | ACTIVE |
| 8 | 42 | Travel | 1881 | FROZEN |
| 9 | 51 | Groceries | 3005 | ACTIVE |

- Each **row** is one thing: one card.
- Each **column** is one fact about it.
- The **id** column gives every row a unique number, so other tables can point at it. The `account_id` column points at a row in the `accounts` table. That pointing is what makes this a **relational** database.

You ask a database questions in a language called **SQL**, such as "give me every card of account 42 that is active". You will learn it in Module 20.

Databases also promise that a change either happens completely or not at all. If the server crashes halfway through moving money, the database undoes the half-finished change. This is called a **transaction**, and for a payments app it is essential.

### Why PayDeck keeps a ledger

You might expect PayDeck to store each balance as one number and change it. It does not. It stores every movement of money in a **ledger**, like a bank statement:

**ledger_entries** (simplified)

| account_id | amount_cents | description |
| --- | --- | --- |
| 42 | +100000 | Opening balance |
| 42 | +2550 | Top-up |
| 42 | −1200 | Corner Café |

The balance is the sum: 100,000 + 2,550 − 1,200 = 101,350 cents, or $1,013.50. If anyone ever asks "why is my balance this?", the answer is right there, line by line. Real banks work this way, and so will you, in Module 24.

## Worked example: following a card payment

When someone pays $12.00 at Corner Café with card 7:

1. The server looks up card 7 in the `cards` table and checks it is `ACTIVE`.
2. It adds up account 42's ledger to check there is enough money.
3. In one **transaction**, it adds a `−1200` row to the ledger and a row to a `card_payments` table.
4. Only when both are saved does it answer "approved".

## Common mistakes

<Aside type="caution" title="Storing money as decimals">
Computers cannot store most decimal numbers exactly: 0.1 + 0.2 comes out as 0.30000000000000004. That is why PayDeck stores **whole cents** everywhere. You will see this bug with your own eyes in Module 4.
</Aside>

## Recap

- A **database** stores data safely, even when the server restarts.
- Data lives in **tables** of **rows** and **columns**; ids let tables point at each other.
- A **transaction** makes a group of changes all-or-nothing.
- PayDeck keeps a **ledger** of every money movement, and works out balances from it.
